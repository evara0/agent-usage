# Skill 作者与来源分类可行性调研

调研日期：2026-10-21（Asia/Shanghai）。状态：研究建议，未实现。

本轮只新增本文，不实施统计功能，不改变 CLI、JSON、现有事件或正式规范，也不创建承诺实施的 OpenSpec change。未来代码、接口、采集和输出变更需要另立 OpenSpec，经总控与用户决定后实施。

## 1. 结论与可行性

可以补充有证据的来源标签和作者声明，不能可靠地给所有 Skill 自动确定唯一作者或四选一类型。建议以“自动收集候选证据 + 用户注册映射 + unknown + 时间快照”逐步推进。

“官方 Skill、开源 Skill、别人写的 Skill、本地新建 Skill”涉及不同问题，不能直接当成互斥分类。官方发行品也可能开源；外部作品可以复制到本地；本地创建的目录可以包含搬运内容；本地改写不会消除原作者。本报告将“官方”限定为 **OpenAI 官方发行**，其他厂商的官方身份需另行核验和标明厂商。

| 要回答的问题 | 可行程度 | 可用证据和前提 | 主要成本与缺口 |
| --- | --- | --- | --- |
| 当前 Skill 属于哪个已安装插件、哪个版本 | 可行，有条件 | 可信运行时/安装记录关联插件 ID、市场、版本与包内路径；包内文件可核对 | 目录扫描只能发现候选；缓存存在不等于当前启用或曾被调用 |
| 当前包是否由 OpenAI 官方发行 | 部分可行 | 官方发布渠道或受信安装记录，与包身份、版本/内容绑定 | 不能只凭 `.system`、`openai-*` 目录、名称或 `author: OpenAI`；本轮未核验安装包签名或发布摘要 |
| 安装/获取来源是仓库、插件目录还是本地复制 | 部分可行 | 安装回执、管理项目发布记录、仓库 URL + 子路径 + 固定提交 | 历史复制常丢失回执；仓库关联不等于实际安装路径可证 |
| 是否有开源许可证 | 部分可行 | 对应版本的许可证文件、包清单声明、文件级例外及适用范围 | GitHub 公开不等于开源授权；声明存在不等于每个资产都受同一许可覆盖 |
| 展示发行方/维护团队 | 部分可行 | 插件发行元数据、官方目录身份、文件声明、用户注册 | 发行方、维护者和原作者不能互换；离线常只能展示“声明发行方” |
| 自动确定原始作者与全部贡献者 | 不可可靠自动判断 | 需可信归属记录、上游历史、人工核实，可能是团队或多人 | 必填元数据不保证作者；仓库 owner、Git commit author/committer 不是完整著作归属证明 |
| 是否由当前用户本地原创 | 不可仅靠目录自动判断 | 用户明确声明，辅以创建/导入/发布记录和版本证据 | 本地文件创建时间、无 remote、初次提交都不能证明原创 |
| 是否本地改写/fork | 部分可行 | 已知上游固定版本与当前完整包摘要/差异；用户说明 | 没有基准时只能 unknown；当前 Git clean 不代表相对上游未改 |
| 给既有历史使用事件确定当时作者 | 多数不可可靠恢复 | 事件时的安装身份和快照，或明确覆盖时间区间的历史记录 | 现有事件不保存该快照；当前安装信息最多提供“按当前信息关联”的候选 |

这里的“可行”指证据和条件足够时可实现，不代表当前 agent-usage 已支持。未进行全量盘点，不能据本轮小样本估计自动覆盖率。

## 5. 建议拆开的维度与字段

以下是待设计的数据概念，不是已确定 schema、CLI 参数或现有 JSON 扩展。不要把它们放进当前 `source` 字段。

| 维度 / 建议概念字段 | 内容建议 | 解释规则 |
| --- | --- | --- |
| 发行身份 `publisher`、`distributionClass` | 组织/团队显示名及可验证标识；OpenAI 官方 / 第三方 / 用户自发发布 / unknown | 官方判断绑定渠道与包版本。未核验的清单值展示为“声明发行方”，不能直接选择官方类别 |
| 原作者 `originalAuthors[]` | 多个个人/组织的公开显示名、角色与证据；unknown 单独标状态 | 不从 publisher、仓库 owner 或最后一次提交者填充；不保存个人邮箱 |
| 维护与改写者 `maintainers[]`、`adaptationAuthors[]` | 当前维护团队及本地改写者，各自独立 | 可与原作者重叠，但不能覆盖原始归属 |
| 获取途径 `acquisition` | bundled / plugin_catalog / git_install / local_copy / local_create / unknown；记录市场与插件身份 | 表示怎么取得当前实例，不判断是否原创；一次实例可以先 git_install 再复制发布，应保留链条 |
| 可追溯源 `upstream` | 脱敏仓库 URL、Skill 子路径、固定 revision、上游实例关联 | refName/main 不是固定版本；fork 仓库与原始上游分开记录 |
| 许可 `license` | declared 标识、版本/范围、证据引用；assessment 为 open_source / proprietary / mixed / unknown | declared 与 verified 分开；缺字段是 unknown，不是 proprietary。公开仓库只是可见性 |
| 本地状态 `localState` | declared_original / imported / adapted / forked / unknown；另有相对已知基准的内容一致/变化状态 | 原创通常依赖用户声明；内容变化只说明差异，不说明谁改的 |
| 发现身份 `installation` | 本地匿名实例 ID、发现范围、市场 ID、插件 ID、包内相对路径、版本/摘要 | scope/path 用于查找与消歧，不提供作者认证；可移植标识与本地路径映射分离 |
| 证据 `claims[]` | 字段值、证据种类/等级、作用范围、观测时间、有效区间、证据摘要/引用 | 每个字段独立定级；有发行方证据不代表作者证据同时成立 |
| 关联 `resolution` | resolved / candidate / unknown / conflict；当前观察或事件时快照；映射版本 | provenance 的确定程度与调用事件是否 inferred 分开 |

展示可以使用多个标签，例如“OpenAI 官方发行（已核验） / MIT（版本许可已核验）”，或“第三方导入（管理记录） / 原作者未知 / 本地适配（用户声明）”。不要为了四类图表强行给未知值选择一个类别。若仍需四个入口，应作为可交叠筛选；同时显示 unknown，并明确不同维度的计数不可直接求和。

## 6. 证据等级、unknown 与冲突

等级描述证据的来源与约束，不是任意事实的通行证。建议所有 claim 同时保留 kind、subject、scope、observedAt、validFrom/validTo 和核验方式。

| 等级 | 证据类别 | 可接受用途 | 边界 |
| --- | --- | --- | --- |
| E1 | 可信安装/发布元数据：官方受信渠道的记录，且绑定包身份、版本或摘要 | 确认某版本的发行渠道/发行方与安装关联 | 本轮未取得完整 E1 链；不能由本地可编辑 author 字段冒充，亦不自动确认包内原创作者 |
| E2 | 可追溯仓库/版本：仓库 + 固定提交 + 子路径 + 内容核对；受管理发布链 | 确认观察内容与某版本的关联，识别 fork/差异 | remote 可改，Git 身份可自填；只存 URL/提交但未比对内容时标“记录待核验”，不能确认原创 |
| E3 | 文件自声明：front matter、插件清单、LICENSE/署名声明 | 展示“声明作者/发行方/许可证”候选 | 复制、搬运、旧模板或恶意文本可伪造；许可证适用范围需单独检查 |
| E4 | 目录、名称和正文关键词启发式 | 发现待审候选、提示检查位置 | 不自动产出官方、原创或开源的确定结论 |
| U | 用户手动声明/注册 | 补齐“本人创建”“本地改写”、昵称与私有来源，按指定范围显示 | 与自动核验并列，不伪装 E1；记录声明时间和适用区间，可撤销 |

处置规则建议：

1. 无证据、文件不存在、权限不足、无法解析或无法联网时，受影响字段保持 unknown，并给出简短原因；不把未知填成当前用户、OpenAI 或第三方。
2. 字段未知与已知空集合不同；例如作者未查明，表达为 status=unknown，而不是让空数组暗示作品无人创作。仅部分作者可知时标 partial，不宣称完整贡献者清单。
3. 同一字段、同一版本、同一时间范围有冲突时保存候选和证据，标 conflict；强证据可支撑推荐值，但不能静默抹去冲突。不同角色/版本的值不必然冲突。
4. 人工 override 是显示/业务映射，保留 user_declared 标记与依据；用户声明不能把来源真实性升级成“自动验证”。E1 与人工声明实质冲突时并列说明。
5. 不自动执行 SKILL.md、安装脚本或包内命令来验证来源。front matter/JSON/YAML 只是不受信数据；限制大小、深度及符号链接扫描范围，防止扩大读取。

## 7. 自动识别和手动注册的方案比较

| 方案 | 优点 | 局限与维护成本 | 建议 |
| --- | --- | --- | --- |
| 仅用路径/名称规则 | 实现快，离线即可 | 错误归属多；缓存迁移、同名、复制、伪造目录立即失效 | 只做候选发现，不能作为最终分类 |
| 仅解析 front matter/插件清单 | 低读盘成本，可得部分声明与命名空间 | 作者常缺；publisher 不是作者；清单可改；默认没有历史 | 作为 E3 证据输入 |
| 自动读取受信安装记录并核对仓库版本 | 自动覆盖更好、可复核 | 安装方式/宿主差异大，固定摘要及回执可能缺失；试验接口不稳定 | 分宿主适配，首期仅使用可验证且稳定的数据源 |
| 仅手动注册映射 | 可覆盖本地原创、私有来源与昵称，离线可控 | 用户录入负担；宽泛别名容易串 Skill；会过期 | 适合最小起点，但必须范围化、版本化 |
| 自动候选 + 手动注册 + 版本快照 | 综合覆盖，保留 unknown 与解释路径 | 需身份解析、冲突合并、时间模型及维护流程 | 推荐渐进路线 |

注册表建议作为单独的本地私有数据，未来再决定存储位置及导入方式；本轮不创建真实注册表。注册项优先精确选择市场/插件/包内 Skill 标识或安装实例，再限定版本/摘要、项目范围和有效区间。纯名称映射只作宽松候选；重名时必须消歧，不使用“第一个找到的目录”。

手工项可声明原作者、本人创建、改写者、来源及证据，不需修改全局 Skill 文件，也不会被插件升级覆盖。可导出的脱敏映射应使用公开标识或匿名根 ID；实际路径映射单独保存在本机，不随项目入库。

## 8. 现有使用事件如何关联，避免伪造历史

本项目代码核对结果：

- `src/types.ts` 的 InvocationEvent 有 skill/fullName、mode、inferred、source、timestamp、sessionId、cwd、sidechain；没有安装实例、插件 ID、Skill 原始路径、revision 或作者快照。
- `src/adapters/codex.ts` 从手动标记、注入和读取推断取得名称；`src/adapters/codex-reads.ts` 即使识别文件读取，也只返回目录名，未保留原始文件路径给事件。不能声称已有事件包含足够的路径证据。
- `src/normalize.ts` 会合并连续重复命名空间并去除版本形状后缀；`src/aggregate.ts` 按规范化 skill 聚合，只保留 fullName 的 aliases 集合。fullName 是采集器保留的原始名称，不是持久安装身份；聚合后更无法精确拆回不同发行版本的次数。
- `docs/usage-contract.md`、`src/contracts.ts` 中报告 source 固定为 codex；事件 source/sources 表示 Codex 等数据来源。不得复用为作者、仓库或安装来源，也不能改变其现有语义。

建议未来保持原始使用计数与 provenance 富化分离，分两种时间语义：

1. **当前资料注释**：对已有 skill/aliases 输出候选资料，并写明“按当前安装信息关联，非调用当时作者”。可以显示候选目录/包的脱敏身份，但不得据此把过去 N 次调用全部归给该作者。没有唯一匹配时为 unknown/conflict，不任意分摊次数。
2. **事件时证据**：未来采集时若确有安装实例/插件/路径和版本证据，将其绑定到不可变 provenance 快照与观测时间。事件引用快照 ID；升级、改名、删除、重装产生新观察，不覆盖旧快照。只有快照或历史回执明确覆盖事件时刻且匹配身份，才可形成可审计的历史归属；应区分当时观测与事后追溯声明。

`observedAt` 不等于 `installedAt`，文件 mtime 不等于创作时间，当前 SHA 不等于调用时 SHA。首次采集快照不能自动回填全部过往时间。用户可以追溯声明某区间，但必须标为 retrospective/user_declared；版本回执也需检验区间空洞、时区和时钟误差。安装记录只覆盖某版本可用期间，不必然证明某个同名调用使用了它。

| 变化/歧义 | 建议处理 |
| --- | --- |
| 作者缺失、团队和多人协作 | unknown/partial；使用数组与角色，允许团队；不把 Git 提交者列表等同作者全集 |
| fork、本地改写、搬运 | 保存原始上游与 fork 的双链、版本差异及改写者声明；保留原作者候选。完全相同的字节也不能证明由哪个渠道取得 |
| 插件命名空间和同名 Skill | 组合市场身份 + 插件 ID + 包内相对路径 + 安装实例；独立 Skill 加 scope/项目范围。插件名本身可重名或伪装 |
| 重命名 | 别名是带时间范围的关系；只有可信迁移记录/人工确认才串联身份，不能因描述相同自动合并 |
| 升级、目录迁移或卸载后仍有历史事件 | 旧快照保留；目录缺失只影响新发现。没有旧快照的历史保持 unknown，不关联到后来占用同一路径的包 |
| 多版本共存、同名记录已经聚合 | 展示多候选/混合或未知，不能把 aggregate.total 复制给每个候选造成重复计数；未来若要分组需单独设计身份与去重兼容策略 |

来源识别成功率与使用计数可靠性是两件事。现有 inferred 的“读取尝试”仍不等于执行成功；即便 provenance 已核验，也不能把调用升级成成功执行。

## 9. 隐私、离线行为和网络成本

建议默认完全离线：只读明确允许的 Skill 根、包清单、安装回执白名单和用户映射。不要为了作者匹配额外读取会话正文、浏览历史、账号配置、Git 凭据或整个个人目录。本轮仅检索公开官方文档，未对本地样本发出仓库查询，也未上传本地内容。

导出只保留必要的公开显示名、组织、公开项目标识和证据摘要；不记录个人邮箱、账号 ID、原始绝对路径或私有仓库地址。本地定位可使用匿名根 ID；路径的普通 hash 仍可能被猜解，不视为匿名化证明。Git URL 必须去掉 userinfo、查询参数、片段及可能含 token 的成分；无法安全解析或未经许可公开的地址应整体隐藏。错误消息也不能回显秘密。

离线无证据时维持 unknown；旧缓存标明 checkedAt/版本与 stale 状态，不把离线失败解释为第三方或闭源。网络核验应由用户选择开启，并明确允许域名/仓库；私有仓库默认不查，禁止自动使用本机凭据。安全域名与重定向校验还应防止不受信清单 URL 引导内网请求。

| 工作 | 成本模型与控制 |
| --- | --- |
| 离线发现与清单解析 | 与允许根中的候选数/元数据字节量相关；设置文件数/体积上限、去重链接目标与缓存，不扫描大型 assets 内容来猜作者 |
| 内容核对 | 单个 SKILL.md hash 较轻，但完整包摘要成本与总字节数相关；仅在版本/文件变化或明确核验时计算，说明摘要覆盖范围 |
| 仓库/目录联网核验 | 按唯一仓库 + 固定版本 + 必需文件缓存，而非每次调用/每条事件请求。首次通常至少取元数据与许可/归属文件，确切请求数取决于供应方接口与分页，不保证固定次数 |
| 失败、限流和更新 | 超时、限并发、请求预算、退避及可取消；使用条件请求/版本缓存，离线继续出结果；不自动 clone 全历史做作者推理 |
| 人工维护 | 新安装、fork、重命名、修改上游时复核；记录映射命中率、unknown/conflict 数，用户按需要补齐，避免要求全量登记才能统计 |
